Fix

Production readiness: CI, security headers, request logging

2026-09-17 (pending commit)
What

Fixed 2 moderate npm audit vulnerabilities (transitive qs via Express) via npm audit fix. Added .github/workflows/ci.yml running the backend test suite and client build on every push/PR to main. Added helmet() (CSP, HSTS, and other security response headers) and morgan (per-request access logging) to server/index.js. Added .github/dependabot.yml for weekly npm update PRs on both the root and client package ecosystems.

Why

Explicit request for a production-readiness plan, scoped down (via a clarifying question) from a broader "make it better" ask -- the user picked production readiness over remaining features, code-quality tooling, or growth/analytics for this round. None of these existed before: no CI meant a broken commit could reach main and then Render with nothing catching it; no security headers on any response; no request-level logging, so Render's log viewer showed nothing about traffic volume, latency, or status codes. Verified helmet's default CSP doesn't break the served React SPA by building the client, booting the server with NODE_ENV=production locally, loading the app in the browser pane, confirming zero console errors and a full accessibility-tree render, and watching a real /chat request round-trip and appear in morgan's access log. A larger, genuinely tradeoff-laden item -- fixing Render's free-tier ephemeral SQLite storage (every redeploy wipes all data) -- was scoped in the same plan but deliberately left unstarted pending the user's choice between a paid Render disk or a bigger sync-to-async database migration.

Decision

Reorganized server/ and test/ into subfolders

2026-09-17 (pending commit)
What

server/'s 25 flat files (everything except the already-grouped adapters/) moved into routes/ (auth, chat, files, finance-news, media -- the Express routers), services/ (memory, personas, suggestions, web-grounding, file-extract -- business logic used by routes), core/ (db, rate-limit, validate, fetch-timeout, response-sanity, sqlite-session-store -- infra/utilities), and routing/ (router, classify, lead, local-adapter, cloud-adapter -- the dispatch/classification system). server/index.js and server/adapters/ stay put. test/ mirrors the same structure, plus a new test/adapters/ for the adapter unit tests.

Why

Explicit request ("organise all project files into a proper format, i dont like files being open randomly") -- 25 alphabetically-sorted, ungrouped files in one folder was the real clutter (client/src/ and everything else was already reasonably sized). Delegated the mechanical move + import-path rewrite to a subagent; it completed every git mv but hit a rate limit before fixing any require() paths, so every fix (~50 call sites across server/, adapters/, and every test file) was done directly afterward and verified file by file. Caught two real regressions the moves alone would have caused, both fixed: scripts/run-tests.js used a non-recursive fs.readdirSync, so with every test file now nested one folder deeper it would have silently run only test/server.test.js and reported success -- rewrote it to walk recursively; and test/core/db.test.js had a require.resolve('../server/db.js') cache-clear call that a path-fixing pass focused on plain require() calls missed, causing one real test failure caught by running the full suite before considering this done. README.md's two stale file-path mentions were also updated; the dated historical planning docs under docs/superpowers/ were deliberately left as point-in-time record, not live documentation.

Cross-conversation memory, crisp answers, cloud-first routing

2026-09-17 11:23
What

Also fixed live: memory-extraction initially used OpenRouter's free auto-router, which landed on a safety/moderation model and returned "User Safety: safe" as a stored "fact" — fixed by reusing whichever adapter had just successfully answered.
